How the embeddings change works

The branch prepares jobs and candidate profiles for semantic matching. Gemini turns selected text into vectors; TiDB stores them for a future matching feature.

Stage 2: data preparation

Based on local commit f9f9f62 on claude/trusting-allen-qomxod, compared with main at 32964b4.

The idea in plain language

An embedding is a list of numbers that represents a piece of text's meaning. This change asks the Gemini embedding API for a 768-number vector for each chosen job or candidate text. Those vectors go into TiDB, the project's SQL database, in VECTOR(768) columns. There is no separate vector database service such as Pinecone or Chroma in this change.

Current limit: this commit stores and refreshes vectors. It does not yet compare vectors, calculate match scores, rank jobs, expose a recommendation endpoint, or add a matching UI.

Follow a save through the system

A backfill command can also enter at step 3 to process records that already exist.

1. SaveA job or candidate profile is saved. A change event is published.
2. QueueAfter the save, a background queue collects IDs for about three seconds.
3. CheckThe indexer builds text and compares its source hash with the stored hash.
4. EmbedChanged text goes to Gemini in batches. Unchanged text is skipped.
5. StoreThe returned vector is checked, normalized, and written to TiDB.

The API call runs outside the user's save request, so saving a job does not wait for Gemini. If an update fails, a later save or backfill can retry it.

Which text is embedded?

StrategyText sent to Gemini
job_full_v1Job title, employment type, work mode, experience, and the full plain-text description.
job_req_v1Job title, experience, and requirement-like sections. If those cannot be found, it falls back to bullets or the full description.
cand_profile_v1Professional headline, desired role, experience, employment and work-mode preferences, and skills. Profiles without a headline, desired role, or skills are skipped.

Candidate name, contact details, pay, work authorization, and resume text are excluded. Job location, salary, and company are excluded from embedding text. The code describes structured filtering as future matching work; that filtering is not implemented here.

What the main files do

ComponentResponsibility
EmbeddingTextsBuilds the exact job or candidate text sent to Gemini.
EmbeddingStrategyNames the three text recipes so stored vectors can be tied to a specific recipe.
SourceHashFingerprints recipe, model, dimensions, and text. Matching hashes avoid repeat API calls.
EmbeddingIndexerLoads records, identifies stale vectors, batches Gemini calls, and saves results.
GeminiEmbeddingClient and EmbeddingServiceMake HTTP requests, retry temporary failures, check vector size, normalize values, and log usage.
JdbcEmbeddingStoreWrites vectors with SQL because the project's JPA mapping does not handle TiDB's VECTOR type.
EmbeddingUpdateQueueProcesses saved records on one background thread.
BackfillJobPages through existing records; supports a dry run and resuming.
AiSchemaMigratorApplies versioned AI SQL scripts and records applied versions.

What TiDB stores

The SQL creates ai_job_embedding and ai_candidate_embedding. A row is identified by the source record ID plus its strategy. It stores the model, dimensions, source hash, source character count, vector, and embedding time. A job normally gets two rows; a candidate with enough profile content gets one. There is no vector index in this version.

Example: a job mentioning “Java backend engineer; Spring Boot and SQL required” creates a full-description input and a requirements input. A candidate profile mentioning “Backend engineer; Java, Spring Boot, SQL” creates a candidate input. Gemini turns them into vectors and TiDB stores them. A later feature could compare those vectors to suggest a match; this commit stops at storage.

When does it run?

  • The website defaults to AI_EMBEDDING_ENABLED=false. When enabled, startup applies the AI table migration and saved jobs or profiles enter the background queue.
  • The backfill Spring profile enables embedding without starting a web server or Redis. It walks existing records by ID.
  • A backfill dry run checks which records need embedding without calling Gemini or writing vectors. Startup may still create the AI tables.
  • Gemini requests default to 50 texts per batch. The client retries selected temporary errors and rejects responses with the wrong vector length.
  • Completed batches are saved as they finish. Running backfill again skips rows whose source hash is unchanged.
A real backfill writes to the configured database and uses Gemini API quota. This guide did not run one.

Practical notes

  • The background queue is in memory. A failed or lost update remains stale until a later save or backfill; this commit does not schedule automatic catch-up.
  • The change adds tests for the new pieces, but its package README says some live Gemini response details had not been confirmed during development.
  • The repository README mentions “TiDB vector search” as the intended direction. The current code has vector columns and writes, but no similarity search query.
