HotDevJobs / implementation overview

Semantic job matching

How job and profile embeddings are created, then used to recommend jobs and find related roles.

Status: This source includes embedding storage, backfill, search, recommendations, and recovery. Runtime matching remains off until AI_EMBEDDING_ENABLED=true, and this page does not indicate whether a deployment has enabled it.

1. Build and refresh embeddings

Job or profile saved
→
Save event queued
→
Text sent to Gemini
→
Vector stored in TiDB

JobPostActivityService and JobSeekerProfileService publish an EmbeddingSourceChanged event. EmbeddingUpdateQueue receives it after commit and groups quick edits. EmbeddingIndexer.index() skips unchanged text, calls EmbeddingService, and saves vectors through JdbcEmbeddingStore.

Job text includes title, work details, experience, and description. Profile text includes headline, target role, experience, preferences, and skills. Names, contact details, and resumes are excluded.

2. Recommend and search

Dashboard recommendations

Stored profile vector → filtered job vectors → cosine scores → Best match order. Comparing stored vectors makes no Gemini call. An explicit Newest or Title sort takes precedence.

Search by meaning

Search phrase → Gemini query vector → filtered job vectors → keyword hits plus related jobs. Keyword hits appear first, including those without a usable vector.

JobPostActivityController applies location, work type, date, and experience filters, then calls SemanticJobSearch.recommendations() or search(). SemanticVectorRepository calculates cosine similarity in TiDB. Stale and low scoring vectors are rejected.

3. Fallback and recovery

Fallback

Missing vectors, Gemini failures, or vector SQL errors leave the existing keyword and profile ranking in place. Structured filters still apply.

Recovery

EmbeddingRecovery scans 50 jobs and 50 profiles per interval and updates missing or changed vectors. Initial backfill covers existing records faster.

Query vectors are cached for 10 minutes. New query embeddings are limited to one at a time and 30 per minute per app instance; excess traffic uses keyword search.

Wiring and dependencies

  • AiEmbeddingConfig creates the beans when AI_EMBEDDING_ENABLED=true. The feature is off by default; Gemini calls also need GEMINI_API_KEY.
  • Key framework imports: Spring ApplicationEventPublisher and @TransactionalEventListener for saves; RestClient for Gemini; JdbcTemplate and NamedParameterJdbcTemplate for TiDB.
  • pom.xml already provides Spring Boot Web/JPA, the MySQL JDBC driver used with TiDB, and Jsoup for extracting job text. This stage adds no Maven dependency.
  • application.properties sets the similarity threshold (default 0.55) and recovery interval (default 5m).

Why 768 numbers? Google recommends 768 as one of the output sizes for gemini-embedding-001. It is one quarter of the default 3072 dimensions, reducing vector storage and comparison work. The service normalizes the shorter vectors, and the TiDB schema uses VECTOR(768). A different size would require a schema migration and re-embedding existing records. Google's embedding guide explains the size options.

The Java test suite passed (135 tests). H2 tests do not execute TiDB vector SQL, so that query still needs a TiDB check before production rollout.
