What changed, and when

Three different states—not one “before and after”

1 · Earlier searchKeyword onlyA phrase had to appear in a job title, description, or company. A synonym with different wording could return nothing.
2 · Semantic code already addedHybrid live searchCommit 0d01bbc added Gemini job/query embeddings, TiDB cosine matching, and keyword-first merging. This is the current production code when AI embedding is enabled.
3 · This workEvaluation harnessA separate eval database, synthetic data, labels, cache, and metrics measure that behavior. The harness did not change the live algorithm or its 0.55 cutoff.

Flow 1 · preparing jobs for semantic search

Each job gets two searchable meaning vectors

01 · SourceJob is saved or updatedThe app queues a refresh; recovery can later find missing or stale vectors.
02 · TextBuild two textsFull posting and requirements-only; location and company are kept as filters, not embedding text.
03 · EmbedCall Geminigemini-embedding-001 returns 768-number vectors. Background indexing batches calls and retries 429.
04 · StoreWrite TiDB VECTOR(768)Two rows per job in ai_job_embedding, with model, dimension, strategy, and source hash.
05 · RefreshSkip fresh vectorsThe source hash detects changed text; unchanged job vectors do not need re-embedding.

Code: EmbeddingIndexer · EmbeddingTexts · EmbeddingRecovery · JdbcEmbeddingStore

Flow 2 · a person searches for jobs

Filters first. Keyword and meaning results then meet.

01 · RequestQuery + filtersFor example, “Java backend” with city “Pune” and an experience range.
02 · Eligible setApply filtersLocation, type, and work mode are SQL conditions; experience is filtered in Java before vector scoring.
03 · KeywordFind literal matchesThe full query is a case-insensitive substring of title, description, or company.
04 · SemanticEmbed + cosine scoreTiDB compares the query vector only with eligible job IDs. Each fresh strategy can score a job; the best score wins.
05 · MergeKeep keyword firstSemantic hits below 0.55 are dropped. Keyword hits get a +1 ranking bonus; newest job breaks ties.
Failure path: if Gemini or vector matching is unavailable, the production search returns its keyword results. The vector query is exact cosine scoring over filtered IDs; this query does not use a TiDB vector index.

Code: JobPostActivityController · keyword SQL · SemanticJobSearch · TiDB cosine SQL

Flow 3 · what the evaluation runner does

A rehearsal on synthetic jobs, not a live search request

01 · GuardRequire eval DBURL name must contain “eval”; the connected database name is checked again before writing.
02 · SeedLoad fictional jobs288 deterministic postings in a separate eval_job table.
03 · CacheEmbed once576 job vectors plus query vectors; save each under a text-hash, model, and dimension key on disk.
04 · Compare40 × 3 × 5Run each query as keyword-only, semantic-only, and hybrid across five similarity cutoffs.
05 · JudgeScore rankingsCompare results with relevance grades 0, 1, or 2; write metrics, latency, call counts, and review queues.

The runner reuses production embedding text and vector SQL. Its eval_job keyword query mirrors the production conditions; it does not call the live HTTP endpoint. Code: database guard · runner · disk cache · metrics

How it is used now

Two independent uses

In the live Job Portal

People use the existing search page. If AI_EMBEDDING_ENABLED=true, Gemini is configured, and job vectors are available, the app adds related semantic matches. There is no new user-facing eval screen or action.

In the eval lab

A developer runs the eval CLI with .env.eval pointing to the separate TiDB database. It writes local Markdown, JSON, CSV, and review files under eval/results/. The final cached run used zero Gemini calls. This cache lives on disk; Redis is not required for the eval. See exact commands.

How to read the scorecard

Four different questions

Precision@5How many of the first five jobs are relevant?
Recall@10How many labeled relevant jobs appear in the first ten?
MRR@10How early does the first relevant job appear?

No-answer accuracy asks whether a query with no suitable job returns nothing. The 0.75 trial passed all three such queries; the 0.55 default passed none. These are provisional labels, so a fresh human-checked holdout is still required.

Decision: keep production at 0.55 until a human-checked holdout supports a change. Method + limitations · Results snapshot
